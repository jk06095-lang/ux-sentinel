# v0.2 Roadmap

## Product Direction

The next version should not merely add more detectors.

The goal is to evolve `ux-sentinel` from:

> a tool that finds UX perception mismatches

into:

> a repair compiler that converts browser evidence into structured constraints a coding agent can implement and a fresh audit can verify.

The core loop becomes:

```text
Observe -> Judge -> Compile repair contract -> Fix -> Re-observe -> Compare
```

The coding agent should not be asked to invent the UX diagnosis again from a vague Markdown report.

## Design Principles

- Keep the deterministic core local-first.
- Preserve inspectable evidence for every blocking decision.
- Separate judge and fixer responsibilities.
- Prefer measurable postconditions over vague style advice.
- Do not weaken safety or hide findings to produce a passing result.
- Treat optional model-based visual review as an extension, not the source of truth.
- Avoid adding a SaaS control plane, account system, hosted runner, or required paid API.

## P0: Repair Loop Foundation

These changes should land before adding large new detector families.

### 1. Replace area-only visual weight with perceptual salience

Current problem:

`visualWeight` is primarily an element-area ratio. It cannot reliably model human attention.

Add a richer, explainable signal:

```text
salience =
  size
+ contrast
+ typography
+ isolation
+ screen position
+ affordance
+ uniqueness
- crowding
- occlusion
```

The exact weights should remain versioned and deterministic.

Proposed output:

```json
{
  "salience": {
    "score": 0.81,
    "size": 0.42,
    "contrast": 0.94,
    "typography": 0.71,
    "isolation": 0.91,
    "position": 0.78,
    "affordance": 0.88,
    "uniqueness": 0.76,
    "crowdingPenalty": 0.12,
    "occlusionPenalty": 0.00
  }
}
```

Suggested files:

- `src/core/salience.ts`
- `tests/salience.test.ts`

Migration:

- keep `visualWeight` temporarily for backwards-compatible evidence,
- add `salience` beside it,
- migrate hierarchy detectors to salience,
- deprecate `visualWeight` as a decision signal after regression coverage exists.

Acceptance criteria:

- identical geometry with different contrast can produce different salience,
- dense clusters reduce effective action prominence,
- primary/secondary hierarchy detectors use the new signal,
- reports expose the component scores that caused the judgment.

### 2. Add a coverage gate

Current problem:

The planner decides what to inspect next, but there is no explicit answer to:

> Have we inspected enough of the experience to stop?

Add a machine-readable coverage model.

Example:

```yaml
coverage:
  primary_goal: covered
  primary_navigation: covered
  empty_state: covered
  loading_state: not_visited
  error_state: not_visited
  modal_open: covered
  modal_close: covered
  recovery_path: not_visited

stop_allowed: false
```

Suggested files:

- `src/core/coverage.ts`
- `tests/coverage.test.ts`

Coverage should be driven by scenario requirements, discovered target categories, and visited state graph nodes.

Acceptance criteria:

- an audit cannot report complete coverage while required scenario states are unvisited,
- coverage explains what remains and why,
- budget exhaustion is reported separately from successful coverage,
- contact sheet and trace manifest expose coverage status.

### 3. Add a structured repair contract

Current problem:

The Codex brief contains findings and suggested fixes, but the fixer still has to rediscover the implementation constraints.

Add `repair-contract.json`.

Example:

```json
{
  "finding": "UX-017",
  "state": "dashboard.empty",
  "target": {
    "id": "t0014",
    "role": "button",
    "text": "Create",
    "bbox": [1184, 82, 92, 32]
  },
  "problem": {
    "type": "primary_action_low_salience",
    "evidence": {
      "salience": 0.31,
      "primaryRank": 4,
      "competingTargets": ["t0007", "t0009", "t0012"]
    }
  },
  "desiredOutcome": {
    "primaryRank": 1,
    "minSalience": 0.65,
    "visibleAboveFold": true,
    "visibleLabelRequired": true
  },
  "preserve": [
    "click behavior",
    "route destination",
    "product terminology"
  ],
  "allowedChanges": [
    "layout",
    "spacing",
    "color",
    "typography",
    "button treatment"
  ],
  "forbiddenChanges": [
    "remove competing functionality",
    "change scenario",
    "hide secondary actions"
  ],
  "verification": [
    "rerun same scenario",
    "target remains clickable",
    "primaryRank == 1",
    "salience >= 0.65",
    "no new P0/P1"
  ]
}
```

Suggested files:

- `src/core/repair-contract.ts`
- `tests/repair-contract.test.ts`

The Markdown Codex brief should become a rendering of this structured contract rather than the primary internal representation.

Acceptance criteria:

- every repairable P0/P1 finding can emit a structured target and desired outcome,
- preservation constraints are explicit,
- verification steps are machine-readable,
- detector suppression or scenario mutation cannot satisfy the contract.

### 4. Add before/after UX delta gates

A finding disappearing is not enough if the patch creates a new problem elsewhere.

Add a small set of explainable dimensions, for example:

- goal clarity,
- action hierarchy,
- navigation scent,
- action feedback,
- recovery,
- scanability,
- accessibility interaction quality.

Do not treat the aggregate as an objective universal UX score. It is a regression and comparison surface.

Example acceptance policy:

```text
P0_after == 0
P1_after == 0
required_goal_success == true
no_dimension_regression > threshold
targeted_dimension_after > targeted_dimension_before
```

Suggested files:

- `src/core/ux-score.ts`
- `src/core/compare-runs.ts`
- `tests/ux-score.test.ts`

## P1: Reduce Fixer Ambiguity

### 5. Semantic goal model

Current scenarios still rely heavily on preferred visible labels.

Move toward:

```yaml
goal:
  intent: create_resource

success:
  state_change:
    resource_count: increase

acceptable_actions:
  semantic:
    - create
    - add
    - new
```

The goal is not to remove visible-copy checks. The goal is to separate:

- what the user wants,
- what action semantics satisfy that goal,
- how the product chooses to label that action.

Suggested changes:

- extend `Scenario` types,
- add goal/intent normalization,
- let visible label evidence remain a usability signal rather than the identity of the goal itself.

### 6. Source attribution

Browser findings should narrow the coding agent's search space.

Target output:

```json
{
  "target": "t0017",
  "source": {
    "component": "EmptyState",
    "file": "src/features/projects/EmptyState.tsx",
    "line": 47,
    "confidence": 0.94
  }
}
```

Possible mechanisms:

- development-only injected `data-ux-source`,
- framework adapters,
- source-map integration,
- runtime component metadata when available.

Requirements:

- never require production instrumentation,
- make attribution confidence explicit,
- do not block repair when attribution is unavailable.

Suggested files:

- `src/core/source-attribution.ts`
- optional framework adapters under `src/adapters/`.

## P2: Optional Visual Critic

Deterministic browser evidence should remain the default.

An optional local visual model may help with ambiguous issues such as:

- hierarchy,
- grouping,
- visual consistency,
- dense layouts,
- subtle competing actions.

Rules:

- disabled by default,
- no required external API,
- output must be advisory and structured,
- model findings must record confidence,
- model output must never bypass browser safety or deterministic verification,
- a model-based recommendation is not accepted until the normal rerun verifies the resulting UI.

Suggested abstraction:

```text
VisualCriticProvider
  -> local disabled/default-none implementation
  -> future local model implementation
  -> optional provider extension point
```

## Proposed v0.2 Pipeline

```text
                 +----------------------+
                 |  deterministic rules |
                 +----------------------+
                           |
Browser evidence ----------+----> UX Judge
                           |        |
                 +---------+        +--> coverage gate
                 |                  +--> UX dimensions
                 |                  +--> repair contract
                 |
                 +--> optional local visual critic
                                      |
                                      v
                                coding agent
                                      |
                                      v
                                  patched UI
                                      |
                                      v
                                fresh UX Judge
                                      |
                                      v
                              before/after gate
```

## Suggested Implementation Order

1. `salience.ts`
2. migrate hierarchy detectors
3. `coverage.ts`
4. coverage artifacts and report rendering
5. `repair-contract.ts`
6. render Codex brief from repair contract
7. `ux-score.ts` and run comparison
8. semantic goal schema
9. source attribution
10. optional visual critic interface

This order intentionally improves deterministic evidence and agent handoff before introducing another model.

## Non-Goals For v0.2

- hosted dashboard,
- user accounts,
- cloud browser fleet,
- autonomous destructive testing,
- generalized web agent,
- replacing Playwright with a vision-only agent,
- automatically redesigning entire products,
- required LLM or VLM API keys.

## Definition Of Done

v0.2 is successful when a coding agent can receive a failed audit and needs substantially less UX inference of its own.

A representative end-to-end test should prove:

1. the initial UI fails for an evidence-backed reason,
2. coverage is sufficient to trust the diagnosis,
3. ux-sentinel emits a repair contract,
4. the fixer changes application code without changing the scenario or detector,
5. the same scenario is rerun,
6. the targeted UX dimension improves,
7. no new P0/P1 finding appears,
8. the evidence bundle proves why the patch was accepted.

At that point, ux-sentinel is no longer only a detector. It becomes a constrained feedback loop between the browser and the coding agent.
